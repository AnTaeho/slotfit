Step 0 — 뼈대 세우기

Step 0의 목표는 집의 골조를 세우는 일과 같습니다. 방마다 벽과 문의 위치를 먼저 정하고, 그중 방 하나에만 가구를 넣어 실제로 살아 볼 수 있게 했습니다.

  • 자리를 정했습니다. 앞으로 만들 모든 파일을 미리 만들고, 각 함수가 무엇을 받고 무엇을 돌려주는지 적어 두었습니다. 이 약속을 코드에서는 타입과 시그니처라고 부릅니다.
  • 길 하나를 끝까지 뚫었습니다. JSON 파일을 읽고 → 가장 단순한 배치 방법(greedy)으로 넣고 → 글자가 넘치는지 검사하고 → 합격 여부를 정하고 → 그림과 표로 내보냅니다.
  • 나머지는 빈칸으로 두었습니다. 더 똑똑한 배치 방법 세 개, 검사 규칙 네 개, 문제를 고치는 단계는 이름표만 붙어 있고 속은 비어 있습니다. 어느 Step에서 채울지 주석에 적혀 있습니다.

입력에서 결과까지 한 바퀴

프로그램이 한 번 도는 동안 일어나는 일을 순서대로 적었습니다. 괄호 안은 그 일을 하는 파일입니다.

  1. JSON 파일을 읽고 모양을 검사합니다. src/io/loader.ts + src/schema/
    템플릿과 콘텐츠 파일을 읽어서, 필요한 항목이 빠졌거나 오타가 있으면 여기서 바로 멈춥니다.
  2. 자주 쓸 정보를 한 번만 계산해 둡니다. src/context.ts + src/tree/traverse.ts
    템플릿은 상자 속 상자 구조라 매번 뒤지면 번거롭습니다. 슬롯만 뽑아 한 줄로 세운 목록 등을 미리 만들어 MatchContext라는 꾸러미에 담습니다.
  3. 매처가 배치를 만듭니다. src/matchers/greedy.ts
    꾸러미를 받아 「어느 슬롯에 무엇을 넣을지」를 정해 MatchResult로 돌려줍니다.
  4. 규칙으로 검사합니다. src/validation/
    규칙을 하나씩 돌려 위반 목록을 만듭니다. 지금 실제로 검사하는 규칙은 「글자 넘침(overflow)」 하나입니다.
  5. 위반이 있으면 고쳐 보고 다시 검사합니다. src/fallback/
    글자 크기를 줄이는 것 같은 대응을 최대 5번까지 시도하는 자리입니다. 지금은 대응 단계가 하나도 없어서 그냥 지나갑니다.
  6. 최종 판정을 내립니다. src/pipeline.ts
    error가 남아 있으면 rejected, warn만 있으면 degraded, 아무것도 없으면 accepted입니다.
  7. 눈으로 볼 수 있게 내보냅니다. src/render/svg.ts · bench/evaluate.ts
    한 건은 그림(SVG)으로, 여러 건은 비교표(마크다운)로 만듭니다.

2번부터 6번까지를 한 함수로 묶은 것이 pipeline.ts의 run()입니다. 이 함수 하나만 이해하면 전체 흐름이 잡힙니다.

src/schema/template.ts — 템플릿의 생김새

가장 먼저 읽을 파일입니다. 이 프로젝트가 다루는 데이터의 모양이 여기 다 있습니다.

export type Box = { x: number; y: number; w: number; h: number };

export type FrameNode = { id: string; type: 'frame'; box: Box; children: TemplateNode[] };
export type GroupNode = { id: string; type: 'group'; box: Box; children: TemplateNode[] };
export type TextSlot = {
  id: string; type: 'text'; role: 'title' | 'subtitle' | 'body' | 'caption'; box: Box;
  fontSize: number; minFontSize: number; maxLines: number;
};
export type ImageSlot = { id: string; type: 'image'; role: 'image'; box: Box };

export type TemplateNode = FrameNode | GroupNode | TextSlot | ImageSlot;
  • 노드는 네 종류입니다. frame(포스터 전체), group(카드), text(글 칸), image(그림 칸). 마지막 줄의 |는 「이 넷 중 하나」라는 뜻입니다.
  • frame과 group은 children을 가집니다. 자식으로 또 노드가 들어가므로 상자 속 상자 구조가 됩니다. 이런 구조를 트리(tree)라고 합니다. 폴더 안에 폴더가 있는 것과 같습니다.
  • text와 image는 children이 없습니다. 트리의 맨 끝이고, 이 둘을 합쳐 슬롯이라고 부릅니다.
  • type 글자로 종류를 구분합니다. 코드에서 if (node.type === 'text')라고 쓰면 TypeScript가 그 안에서는 node를 TextSlot으로 알아봅니다.

파일 아래쪽의 …Schema들은 같은 모양을 한 번 더 적은 것입니다. 위쪽 타입은 코드를 쓸 때 TypeScript가 검사하는 용도이고, 아래쪽 스키마는 프로그램이 실행될 때 JSON 파일을 실제로 검사하는 용도입니다. 타입은 실행되면 사라지기 때문에 둘 다 필요합니다. 스키마 검사는 zod라는 라이브러리가 맡습니다.

z.lazy(() => …)는 자기 자신을 포함하는 모양(children 안에 또 노드)을 적을 때 쓰는 장치입니다. 「필요해질 때 가서 확인해라」라는 뜻이라고만 알아 두면 됩니다.

export type MatchResult = {

src/tree/traverse.ts — 트리에서 슬롯만 뽑아 한 줄로 세우기

export function collectSlots(root: TemplateNode): Slot[] {
  if (root.type === 'text' || root.type === 'image') return [root];
  return root.children.flatMap(collectSlots);
}

두 줄짜리 함수지만 이 프로젝트에서 처음 만나는 재귀입니다. 재귀는 함수가 자기 자신을 다시 부르는 것입니다.

  • 지금 보는 노드가 슬롯이면, 그것 하나를 담은 목록을 돌려줍니다.
  • 슬롯이 아니면(frame이나 group이면) 자식들 각각에게 같은 질문을 하고, 받은 목록들을 이어 붙입니다. flatMap이 「각각에게 묻고 이어 붙이기」를 한 번에 합니다.

t01 템플릿으로 따라가 보면 이렇게 됩니다.

root (frame)
├─ title                    → [title]
├─ cardA (group)
│  ├─ cardA-sub             → [cardA-sub]
│  └─ cardA-body            → [cardA-body]
└─ cardB (group)
   ├─ cardB-sub             → [cardB-sub]
   └─ cardB-body            → [cardB-body]

결과: [title, cardA-sub, cardA-body, cardB-sub, cardB-body]

위에서 아래로, 안쪽을 다 본 뒤 다음 형제로 넘어가는 이 순서를 DFS(깊이 우선 탐색)라고 합니다. greedy가 슬롯을 채우는 순서가 바로 이 순서입니다.

같은 파일의 slotGroupMap은 「각 슬롯이 어느 카드 소속인가」를 적은 표를 만듭니다. cardA-sub → cardA, title → null(어느 카드에도 속하지 않음) 같은 식입니다. Step 3에서 카드가 찢어졌는지 볼 때 씁니다.

src/matchers/types.ts · greedy.ts — 첫 번째 배치 방법

export type Matcher = { name: string; match(ctx: MatchContext): MatchResult };

매처의 약속은 이 한 줄입니다. 이름이 있고, 꾸러미를 받아 배치를 돌려주는 match 함수가 있으면 매처입니다. 앞으로 만들 네 가지 방법이 모두 이 약속을 따르기 때문에, 나머지 코드는 어떤 매처가 오든 똑같이 다룰 수 있습니다. 콘센트 규격이 같으면 어떤 가전이든 꽂을 수 있는 것과 같습니다.

function match(ctx: MatchContext): MatchResult {
  const used = new Set<string>();          // 이미 쓴 콘텐츠 id를 적어 두는 메모장
  const assignment: Assignment = [];
  let totalCost = 0;

  for (const slot of ctx.slots) {          // 슬롯을 DFS 순서로 하나씩
    const item = ctx.content.items.find(   // 콘텐츠를 앞에서부터 훑어
      (i) => !used.has(i.id) && i.kind === slot.type,   // 아직 안 썼고 종류가 같은 첫 번째
    );
    if (item === undefined) {              // 넣을 것이 없으면 빈칸으로
      assignment.push({ slotId: slot.id, contentId: null });
      continue;
    }
    used.add(item.id);
    assignment.push({ slotId: slot.id, contentId: item.id });
    totalCost += cost(item, slot, ctx);
  }

  const dropped = ctx.content.items.filter((i) => !used.has(i.id)).map((i) => i.id);
  return { assignment, dropped, totalCost };
}

greedy(탐욕)는 「지금 눈앞에서 제일 먼저 보이는 것을 집는다」는 방식입니다. 줄 선 순서대로 빈자리에 앉히는 것과 같습니다. 역할도, 글 길이도, 카드 소속도 보지 않습니다.

src/pipeline.ts — 전체를 잇는 함수 run()

export function run(t: Template, c: Content, matcher: Matcher): PipelineResult {
  const ctx = buildContext(t, c);                 // 꾸러미 만들기
  let r = matcher.match(ctx);                     // 배치
  let adj = { fontSize: {} };                     // 아직 조정한 것 없음
  let violations = validate(ctx, r, adj);         // 검사

  for (let i = 1; i <= MAX_ITERATIONS && violations.length > 0; i++) {
    const step = POLICY.find((s) => s.applies(violations));  // 쓸 수 있는 대응 찾기
    if (step === undefined) break;                // 없으면 그만
    const next = step.apply(ctx, r, adj);         // 대응 적용
    r = next.r; adj = next.adj;
    violations = validate(ctx, r, adj);           // 다시 검사
  }

  return { status: decideStatus(violations), /* … */ };
}

(읽기 쉽게 기록용 줄을 뺀 모양입니다.) 가운데 for 반복이 「위반이 있으면 고쳐 보고 다시 검사」하는 자리입니다. 대응 목록인 POLICY가 지금은 비어 있어서 첫 바퀴에서 바로 빠져나옵니다. 병원에 비유하면 검사 → 처방 → 재검사를 최대 다섯 번 되풀이하는 구조인데, 아직 처방전이 한 장도 없는 상태입니다.

function decideStatus(violations: Violation[]): Status {
  if (violations.some((v) => v.severity === 'error')) return 'rejected';
  if (violations.some((v) => v.severity === 'warn')) return 'degraded';
  return 'accepted';
}

판정은 세 줄입니다. error가 하나라도 있으면 거절, warn만 있으면 「쓸 수는 있지만 흠이 있음」, 아무것도 없으면 합격입니다. 이것은 Step 0 때의 초안이고, Step 4에서 「fallback이 손댄 결과도 degraded」로 넓혔습니다(D-22, 아래 Step 4 장).

결과의 trace에는 무슨 일이 있었는지가 순서대로 적힙니다. 이번 실행에서는 「match(greedy)… → validate: error 1, warn 0 → fallback: 적용할 단계 없음」 세 줄입니다.

src/matchers/costMatrix.ts — 점수표를 정사각으로 만들기

회식 자리 배치를 떠올리면 쉽습니다. 사람(콘텐츠)마다 자리(칸)별 불편 점수가 있고, 전체 불편 합이 가장 작은 자리표를 찾고 싶습니다. 자리가 모자라면 「집에 가기」 자리를, 사람이 모자라면 「빈 의자」를 더해 표를 정사각으로 만듭니다. 그러면 「누구를 어디에, 누구를 보낼지, 어디를 비울지」가 한 번에 정해집니다.

항목 a(priority 2), b(priority 3), 칸 S(body) 하나로 예를 듭니다. cost(a,S) = 4, cost(b,S) = 3이라고 합시다.

             S     집에가기  집에가기
a            4        30        30
b            3        10        10
빈 의자     10         0         0
  • a→S, b→집, 빈 의자→집: 4 + 10 + 0 = 14
  • b→S, a→집, 빈 의자→집: 3 + 30 + 0 = 33
  • a·b 모두 집, 빈 의자→S: 30 + 10 + 10 = 50

b가 S에 더 잘 맞는데도(3 < 4) 답은 a→S입니다. a를 버리는 값(30)이 b를 버리는 값(10)보다 훨씬 크기 때문입니다. 점수표 하나가 「잘 맞는가」와 「버려도 되는가」를 같이 저울질합니다. 표의 크기는 항목 수 + 칸 수입니다. 이 예시는 2 + 1 = 3이고, t04×c05는 10 + 10 = 20입니다.

src/matchers/hungarian.ts — solveAssignment()를 3×3 표로 따라가기

모든 자리표를 다 시험하면 20×20 표에서 20! ≈ 2.4×1018가지입니다. Hungarian은 행을 한 줄씩 추가하면서 「지금까지 들어온 사람만으로 최선인 자리표」를 유지해 N³ 정도의 계산(20³ = 8,000)으로 끝냅니다.

핵심 장치는 잠재값 u[행], v[열]입니다. 「줄인 비용」 = 원래 값 − u − v가 어디서나 0 이상이 되도록 유지합니다. 모든 사람이 줄인 비용 0인 칸에 앉으면, 그 합은 Σu + Σv와 같고 어떤 자리표도 그보다 작을 수 없습니다. 그래서 그것이 최적입니다.

위 3×3 표를 실제 코드로 돌린 기록입니다.

== 행 1 (a) 추가
  a가 갈 수 있는 열 중 줄인 비용 최소 = S(4) → delta 4, S는 빈 열
  u = [4, 0, 0]  v = [0, 0, 0]       a → S
== 행 2 (b) 추가
  b의 최소 = S(3), 그런데 S에는 a가 앉아 있다 → delta 3, a를 트리에 넣음
  a를 S에서 빼면 a의 다음 칸(집, 30)은 +26 비싸다
  b가 다음 칸(집, 10)으로 가면 +7 → delta 7, 빈 열(집)에 닿음
  u = [11, 10, 0]  v = [-7, 0, 0]    a → S, b → 집
== 행 3 (빈 의자) 추가
  남은 집 열의 줄인 비용 0 → delta 0, 바로 앉음
  최종: a → S, b → 집, 빈 의자 → 집
  Σu + Σv = 11 + 10 + 0 − 7 = 14  (= 실제 합 14)

2번째 행에서 일어난 일이 Hungarian의 전부입니다. 새로 온 사람이 이미 찬 자리를 원하면 「기존 사람을 밀어내고 그 사람이 다음 자리로 가는 비용」과 「새 사람이 다음 자리로 가는 비용」을 비교해서 더 싼 쪽으로 자리를 한 칸씩 밉니다. 코드에서 minv[j]가 「지금까지 본 사람들에서 열 j까지의 최소 추가 비용」, way[j]가 「그 길의 직전 열」이고, 마지막 do … while이 way를 거꾸로 따라가며 자리를 미는 부분입니다.

src/matchers/hierarchical.ts — match()의 네 단계

  1. 카드끼리의 비용표. 콘텐츠 카드(같은 groupId 묶음) g와 템플릿 카드 h마다 solveSubproblem(g의 항목들, h의 칸들)로 안쪽을 Hungarian으로 풀고, 그 최소 비용을 표에 적습니다.
  2. 카드끼리 Hungarian. 그 표로 카드 짝을 정합니다. 짝 없는 콘텐츠 카드는 「항목 전부 버림」 비용, 짝 없는 템플릿 카드는 「칸 전부 비움」 비용입니다.

  4. 나머지. 카드에 속하지 않은 항목(제목 등)과 짝을 못 찾은 카드의 항목을, 카드 밖 칸과 짝 없는 카드의 칸에 flat Hungarian으로 넣습니다.

2단계에서 카드 짝을 정할 때는 「제목이 갈 곳이 남는가」를 보지 않습니다. 카드가 칸 두 개를 다 가져가고, 4단계에서 제목은 갈 곳이 없어 버려집니다. 이 결정의 이유(D-19)는 이렇게 정리했습니다. 카드가 찢어졌는지는 두 짝을 함께 봐야 알 수 있어 짝별 점수로는 표현할 수 없습니다. 계층 매칭은 빠르고 단계마다 손으로 설명할 수 있습니다. 그리고 이런 실패는 「priority 1 유실」로 드러나므로 Step 4의 검사가 거절로 잡을 수 있습니다. 섞인 카드라는 틀린 정보를 내보내는 것보다, 드물게 거절하는 편이 낫다고 판단했습니다.

src/fallback/steps/ — 대응 두 단계 (D-21)

  1. shrinkFont. 넘친 칸의 글자 크기를 1px씩 내려 들어가는 가장 큰 크기를 찾습니다. minFontSize 아래로는 내리지 않습니다. 정보를 잃지 않으므로 먼저 합니다.

두 단계 모두 입력을 고치지 않고 새 결과와 새 adjustments를 돌려줍니다. 계약도 조금 바꿨습니다. applies(위반, ctx, 결과, 조정값)처럼 현재 글자 크기를 볼 수 있게 해서, 이미 최소 크기인 칸에 shrinkFont가 헛도는 일을 막았습니다(D-23).

export function decideStatus(violations, fallbackCount): Status {
  if (error가 하나라도 있음) return 'rejected';
  if (warn이 있음 || fallbackCount > 0) return 'degraded';
  return 'accepted';
}

예상 질문과 답의 뼈대

「greedy가 왜 부족했나요?」 입력 순서와 칸 순서만 봐서, 제목이 세 번째로 들어오면 제목 칸에 소제목이 들어갑니다. golden 0.43.

「cost 가중치는 어떻게 정했고, 바꾸면 어떻게 되나요?」 「p1 보존 ≫ 제목 칸 채움 > p2 보존 > 역할 > 넘침 > 순서·짧음」의 우선순위가 나오게 정했습니다. p2 버림 비용을 역할 벌점보다 낮추면 t08×c07에서 기간·본문을 캡션 칸에 넣는 대신 버립니다.

「Hungarian의 시간 복잡도는? 칸이 1,000개라면?」 표 크기 N = 항목 + 칸에 대해 O(N³)입니다. N = 2,000이면 약 8×10⁹번 연산이라 수 초 단위입니다. 카드 단위로 나누는 계층 매칭이 문제를 작게 쪼개는 효과도 있습니다.

「Hungarian이 맞다는 걸 어떻게 확인했나요?」 모든 경우를 시도하는 bruteForce와 무작위 입력 수백 개에서 totalCost가 같은지 fast-check로 비교합니다.

「계층 매칭이 최적이 아닌 경우는? 왜 감수했나요?」 t09×c09에서 카드가 칸을 다 차지해 p1 제목이 버려집니다(1007.5 대 56.5). 카드 찢어짐은 짝별 점수로 표현할 수 없고, 이 실패는 priorityDropped error로 거절되어 드러납니다.

「invariant와 validation 규칙의 차이는?」 invariant가 깨지면 코드 버그(테스트 실패), 규칙이 깨지면 결과물의 품질 문제(대응하거나 거절)입니다.

「무엇을 거절했나요?」 error가 남은 결과입니다. p1 본문 12개(c10), 줄여도 안 들어가는 p1 고지문(c11), 그리고 F-7 경우입니다.

「golden의 주관성은?」 정답은 Claude가 「디자이너라면」 기준으로 썼고 파일마다 판단 근거를 note에 남겼습니다. 카드 순서 차이는 오답으로 세지 않습니다(D-7).
